# ADR 0001：服务端产物在构建期自包含

## Status

已采纳（2026-11-02）。

## Context

项目模式与打包模式共用一条服务端交付链路，但服务端产物曾经把第三方 npm
依赖留给运行时 Node 解析：`build` 生成的项目 server 与内置/本地插件服务端入口
保留裸导入，依赖项目根或插件目录的 `node_modules`。这在开发期成立；进入打包
形态后，产物被释放到桌面数据目录，用户插件装进
`<桌面数据目录>/plugins/<id>@<version>/`，项目 `node_modules` 既不在产物里，
也不在解析路径上。一个在 `dev` 里正常的 `dayjs` 导入，到了桌面形态就会启动失败。

当时有两种备选方案：

1. 让每个插件目录在运行时携带自己的 `node_modules`，由 Node 解析依赖。
2. 增加第二个 `distribution` 预设，与开发/构建预设并存。

方案 1 会把平台相关文件、符号链接与完整依赖树带进插件包，和构建期资产管线的
模型不一致，也让内容 hash 与跨平台安装不稳定。方案 2 会增加第二套服务端构建
模式，与「项目模式只有一套规则」冲突，作者还要判断当前该用哪个预设。

## Decision

采用唯一规则：**非框架提供的额外包由模块作者在构建期自包含**。服务端产物不再
依赖项目或插件目录的 `node_modules`。

- `serverPreset` 默认用 esbuild 打包第三方依赖；保持 external 的只有 Node 内置
  模块（`node:*`）与 `cordis-app` 的类型面。
- `@cordis-app/*` 是框架内部包，不属于公开的框架提供依赖；值导入在构建期失败。
- `dev`、`build`、`start`、`package:desktop` 与签名插件安装五条路径共用这一条
  规则，不增加 `distribution` 预设、开关或环境变量。
- `build` 的 `dist/` 与 `.cordis-plugin` 归档都不包含 `node_modules`；
  `package.json.dependencies` 只是构建输入，运行时不安装。
- `package:desktop` 把白名单外的裸导入当作发布前的硬错误，避免把不完整产物装进
  安装目录。
- 原生 `.node` addon 不在当前范围内；`ws` 的可选原生依赖由共享的 esbuild 片段
  置空并强制走纯 JS 回退。

## Consequences

正面：

- 产物搬到任何目录、删除项目 `node_modules`、或从签名插件包安装后都能直接运行，
  不需要 npm 或网络。
- 插件包更小，内容 hash 更稳定，跨平台安装不携带平台相关文件。
- 作者只需要使用普通 npm 包与预设，不需要维护 vendor 目录或专属安装流程。
- 框架只维护一个服务端预设，`dev` 与发布产物行为一致，问题更早暴露。

代价：

- 每个插件各带一份第三方依赖，重复依赖会增加产物体积；模块级单例状态不跨插件
  共享，插件需要用 `ctx` 提供的能力共享数据与缓存。
- `dev` 的每次重建都会重新打包依赖，项目较大时更重。
- 原生 `.node` addon 不受支持，需要改用纯 JS/WASM 或把能力放到服务端。
- 作者若忘记把依赖写进 `package.json`，构建期会报解析错误；发布前扫描会再拦截
  遗漏的裸导入。
