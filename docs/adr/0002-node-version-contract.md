# ADR 0002：单一 Node 版本契约，最低 Node.js 24

## Status

已采纳（2026-11-02）。

## Context

仓库对 Node 版本的声明曾经互相矛盾，作者与用户无法从任何单一位置判断到底支持
哪个版本：

- 根 `package.json` 与公开的 `cordis-app` 包声明 `engines.node: ">=22.18.0"`，
  CI 也固定 `22.18.0`。
- 服务端预设的构建目标是 `node24`，桌面 runtime 打包器的目标却是 `node22`。
- `@types/node` 已是 24 线，类型检查会放行 Node 24 才有的 API。
- 桌面安装目录直接复制打包者的 `process.execPath`，因此随包 Node 可能是 22.18，
  也可能是 24。

最具体的故障场景发生在桌面打包：打包者在 Node 22.18 上执行 `package:desktop`，
安装包随包提供的 Node 就是 22.18；但服务端预设按 `node24` 输出代码，只要项目或依赖
用到 Node 24 专属语法，安装包就会在自己的随包 Node 上启动失败。类型层也会误导
开发者：在 22.18 上可以写出类型检查通过、运行时才失败的代码。

问题不在某一个版本号写错，而在「开发、构建、CLI、服务端产物、桌面随包 Node」
各自按不同版本理解契约。22.18 这个下限原本来自测试脚本直接运行 TypeScript，
依赖 Node 22.18 的默认类型剥离；这项特定下限在统一到 24 后不再需要。

## Decision

采用单一 **Node 版本契约**：最低运行版本为 Node.js 24（`>=24.0.0`），开发、构建、
CLI、项目与插件的服务端产物、桌面随包 Node 全部按这个下限对齐。

- 服务端预设与桌面 runtime 打包器共用同一个 `node24` 构建目标；两者引用同一个
  共享常量，不各自硬编码。浏览器目标保持 `es2022`，不属于 Node 版本契约。
- `@types/node` 统一到 24 线，类型面以最低运行版本为准，避免放行更高版本才有的
  API；不承诺精确到 24.0.0 的类型 API 差异。
- CI 覆盖 Node 24 线的 `24.22.2` 与当前最新 LTS `26.13.0`；Go 外壳 job 使用
  `24.22.2`。
- 桌面 `package:desktop` 继续复制打包者的 `process.execPath`；打包环境要求
  Node.js ≥ 24，安装包随包提供该 Node，最终用户不需要安装 Node。
- 契约只承诺使用 `serverPreset` / `clientPreset` 构建的插件产物；自定义 esbuild
  配置不在契约内。不新增 `bundle.json` 的 target 字段，也不做插件 JS 语法扫描。
- 不加运行时 Node 版本检查；`engines`、CI、README 与 ADR 是契约的表达方式。
- 不固定、下载或内置某个 Node 版本；随包 Node 的版本由打包者决定，使用 24 或 26
  都满足契约。
- 不记录支持期限或 EOL 日期；本 ADR 只定义当前最低版本与对齐规则。

## Alternatives

**保留 Node 22.18。** 这能保持现有 `engines` 与 CI 不变，但必须把服务端与桌面
target、`@types/node` 全部退回 22 线，才能让声明、产物与类型三者一致；这会放弃
Node 24 的语法与 API，也要继续维护一个仅为测试脚本服务的下限。真正的故障来自
「声明 22、构建 24、类型 24」的混用，保留 22.18 不解决冲突，只是把冲突固定下来。

**把最低版本提升到 Node 26。** 26 可以作为 CI 的最新 LTS 覆盖，但把它写成最低
运行版本会排除仍在 24.x 的用户，而当前没有任何必须依赖 26 的构建目标或 API。26
上的可用性由 CI 矩阵验证即可，不需要抬高最低运行版本。

**只改 `@types/node`，不改运行时。** 把类型退到 22 线能减少类型层的误导，但
`engines`、CI、服务端与桌面构建目标仍然互不一致，桌面随包 Node 仍可能在 Node 22
上启动 Node 24 产物。类型只是契约的一个表面，单独修正类型不构成契约。

## Consequences

正面：

- Node 的最低运行版本只有一个答案，开发、构建、CLI、服务端产物与桌面随包 Node
  不再各自漂移。
- 服务端预设与桌面 runtime 共用构建目标，两条链路不会再次分叉。
- 类型面与最低运行版本对齐，不会出现类型检查通过、运行时缺少 API 的代码。
- 最终用户的安装与启动流程不变：安装包自带 Node，不需要预装。

代价：

- Node 22 不再受支持。Node 22 上的行为可能是底层语法错误、API 缺失或包管理器
  警告，不作为兼容目标。
- 打包者必须在 Node.js ≥ 24 的环境中执行 `package:desktop`；随包 Node 的版本
  取决于打包者，安装包之间可能不同。
- 类型面跟随 24 线，不能使用 25 及以上版本才有的类型 API。
- 自定义 esbuild 配置的插件产物不在契约内，作者需要自行保证构建目标不低于其
  宿主运行版本。
- 不新增运行时检查，Node 版本不满足时可能直到产物加载才暴露失败。
