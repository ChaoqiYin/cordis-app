# ADR 0007：入口地址是会话身份，外壳补齐浏览器 chrome

## Status

已采纳（2026-11-11）。

## Context

桌面外壳取代了浏览器窗口，却没有提供浏览器最基本的两个保证。

**没有重新载入入口。** 用 `cordis-app dev --shell` 开发时，改了前端文件、窗口
仍是旧界面，而外壳没有任何恢复手段：`⌘R` 没有反应，菜单里也没有「重新载入」。
WKWebView 自身不带刷新快捷键，页面与 Vite 脱节后只能 kill 整个进程组重启外壳，
窗口位置与服务状态一起丢失。

**入口地址会漂移。** 窗口在启动时导航到 `http://127.0.0.1:<vite 端口>/#token=…`
一次，之后不再更新；而 Vite 允许「5173 被占就自动换端口」。端口一变，页面的
HMR 客户端仍连旧 origin，永远回不来，页面永久停在旧代码上，且无法在窗口内自证。
浏览器标签页同理：刷新后可能指向一个不同的端口。

这与既有约束并不冲突，但需要写清楚边界。ADR 0003 规定外壳不解析配置、不代理
HTTP、不在页面与后端之间传话，原生能力只经 worker 的 `ctx.native` 暴露；ADR
0006 规定连接提示等界面归 body，壳不直接操作 DOM。重新载入既不能变成页面与外壳
之间的新通道，也不该变成 body 的责任。

本 ADR 记录两条不变式，供后续改动判断：**进入页面 URL 的端口都是会话身份**，
**外壳替代浏览器 chrome，必须提供重新载入等基础逃生口**。

## Decision

### 1. 入口地址的端口是会话身份，必须在会话开始前固定

- 开发会话开始前确定 Vite 端口：显式 `--port` 时使用用户值；否则优先尝试
  5173，被占用时用现有的 `findFreePort` 分配。两种情形都以 `strictPort: true`
  启动，Vite 不得自行换端口。
- `strictPort` 与 `host`、`proxy`、`root` 一样属于框架必须保住的项：项目级
  Vite 配置合并后重新钉住，项目配置不能把它们改回去。
- 端口分配顺序保证 Vite 端口与 worker 端口不同：外壳模式先确定 Vite 端口，
  再分配 worker 端口并避开它；浏览器模式 worker 先启动，再分配 Vite 端口并
  避开 `app.port`。
- 绑定失败一律映射为「端口不可用」错误。Vite 以 `EADDRINUSE` 失败时，由 CLI
  的开发服务器启动封装转换成专用错误类型，与现有的外壳端口冲突错误并列；不
  让 Vite 静默换端口。
- 外壳模式的整轮重试同时覆盖 Vite 端口冲突与外壳端口冲突：关闭本轮 Vite、
  重新分配 Vite 与 worker 端口、重新启动外壳；沿用现有的最大尝试次数，耗尽后
  以明确文案失败。浏览器模式同样按相同上限重试。
- 窗口入口地址仍由外壳用「CLI 传入的 Vite 地址 + 握手 token」拼接，不新增
  CLI→外壳的运行期地址通道。地址的稳定性由端口分配保证，而不是由地址订阅
  保证。
- 开发地址的含义不变：浏览器模式打印实际 URL；外壳模式仍不打印开发地址。

这条不变式的直接结果：Vite 因配置变更重启时回到同一 origin，HMR 重连即可
恢复；浏览器标签页刷新、外壳窗口重新载入后都指向同一地址，不会掉鉴权。

### 2. 重新载入是外壳的窗口原语

- 窗口后端接口增加执行页面脚本的原语（`Eval` 一类），`webview` 句柄本身提供
  该能力；「重新载入」由窗口控制器在该原语上实现为 `location.reload()`。
- 窗口控制器提供两条等价路径：一条供非 UI 线程调用（投递到 UI 线程后执行），
  一条供已在 UI 线程的回调直接执行。**菜单回调必须走后者**：从 UI 线程再
  `Dispatch` 回 UI 线程会自锁。来自 worker 的原生窗口命令仍按 ADR 0003 经
  `Dispatch` 投递；直接路径只服务已在 UI 线程的壳内回调。
- 平台 chrome 按现有平台分文件模式新增独立文件，不塞进窗口命令实现文件。
  macOS 注册最小主菜单并添加「重新载入」项，`⌘R` 为等价键；Windows/Linux
  先提供可编译的空实现。
- chrome 在窗口创建后安装一次，安装时机与 `windowController.attach` 保持同样
  的先后关系：窗口可用之前不接受菜单动作；窗口关闭/销毁后，菜单动作不得再
  触达已销毁的窗口。降级路径（`--url`、没有 WebView 运行时）不安装 chrome。
- 所有运行形态（项目模式与打包模式）都安装菜单，**不引入 `dev` 条件分支**。
  外壳取代了浏览器窗口，就应提供浏览器 chrome 的逃生口；形态分叉会让打包形态
  在页面异常时无路可走。若担心误刷丢状态，应由 body 自己持久化，而不是移除
  刷新。
- 刷新使用当前 URL 重新载入，不重新导航、不改窗口尺寸/标题/焦点。会话 token
  已存在 `sessionStorage`，同一 origin 下重新载入后仍可读取，不会出现「缺少
  会话 token」。
- 不通过注入 JS 键盘监听实现快捷键：那是页面与外壳的耦合，且会被页面代码
  拦截。

### 3. 不扩大协议与运行期通道

- **不把 `window.reload` 加入原生能力契约**，`NATIVE_CONTRACT_VERSION` 保持
  **1**。原生契约承载项目与插件需要的稀缺系统能力；刷新在页面内用
  `location.reload()` 即可完成，进契约需要升版本、双侧同步与权限模型改动，
  当前没有消费者。
- 不把 supervisor 的握手从「启动读一次」改为「地址订阅」，也不新增 CLI→外壳
  控制通道。地址漂移由固定端口消灭；订阅式地址更新留给将来支持远程 dev
  server 或多窗口时再讨论。
- 不监听 HMR 断线并自动整页刷新：它不能解决地址漂移，只会在旧端口上循环。

### 与既有 ADR 的关系

- **ADR 0003**：外壳仍然保持最小——`Eval` 是窗口控制器内部的一次性窗口原语，
  不经过 worker，不成为页面可调用的命令，也不改变外壳「不拦截导航、不向页面
  注入监听或绑定、不代理 HTTP」的定位。原生命令表与契约版本不变。
- **ADR 0006**：连接提示等界面归 body；重新载入属于窗口原语，body 不需要注册
  任何东西，外壳也不通过刷新去修改页面 DOM 或布局。

## Alternatives

**保留 Vite 的自动换端口。** 改动最小，但入口地址变成运行期事实：握手时传入
的 `devUrl`、窗口已导航的地址与 Vite 重启后的监听地址可能互不一致，HMR 客户端
无法自行纠正。地址漂移正是本 ADR 要消灭的问题。否决。

**由 supervisor 或 CLI 向窗口推送地址更新。** 能覆盖远程 dev server 与多窗口，
但要把握手从「启动读一次」扩成订阅协议，并新增 CLI→外壳控制通道，扩大外壳与
supervisor 的职责。端口固定后没有消费者，暂时不做；保留为将来支持远程 dev
server 时的方向。

**向页面注入 `Cmd/Ctrl+R` 键盘监听。** 省去平台菜单代码，但把刷新变成页面与
外壳的耦合：页面代码可以拦截或覆盖监听，浏览器模式也没有对应实现，且不符合
平台快捷键应由宿主注册的惯例。否决。

**把 `window.reload` 加进原生能力契约。** 项目和插件都能显式调用，语义统一；
但刷新不需要任何系统权限，页面本来就能做，进契约要升 `NATIVE_CONTRACT_VERSION`、
双侧同步并补权限模型，当前没有消费者。否决。

**只在开发模式提供重新载入。** 降低误刷丢状态的产品风险，但打包形态在页面白屏
或卡死时同样无路可走，用户被迫重启整个应用；形态分叉还会让「为什么开发能刷新、
打包不能」成为长期解释成本。否决。

## Consequences

正面：

- 入口地址在整个会话内不变；Vite 重启后 HMR 重连即恢复，浏览器标签页刷新与
  窗口重新载入都指向同一 origin。
- 所有运行形态都获得与浏览器一致的重新载入入口；项目与插件不需要感知，页面
  仍是普通网页。
- 原生契约、权限模型、协议类型都不变；改动集中在 CLI 端口分配与外壳窗口层。
- 端口冲突从「Vite 静默换端口」变成显式错误与整轮重试，用户能看到发生了什么。

代价：

- 默认端口被占时由 CLI 在会话开始前分配，不再依赖「Vite 监听时自己换一个」
  的隐式行为；打印的地址才是权威，脚本里硬编码 5173 的用户需要显式 `--port`。
- 端口分配与实际监听之间仍有竞争窗口，只能靠重试收敛；尝试次数耗尽后启动失败。
- 重新载入会丢失页面内存状态（React 状态、未提交表单），这是浏览器的正常语义，
  不做额外状态恢复。
- macOS 菜单涉及 ObjC 运行时调用，改动必须集中在平台文件内，并保证其它平台的
  空实现让 `go test ./...` 在各平台继续通过。
- Windows/Linux 暂时没有真实菜单，那里的菜单式重新载入在实现前不可用；快捷键
  的跨平台约定要等对应平台实现后再补齐。
