# ADR 0006：重启原因进入协议，连接提示归 body

## Status

已采纳（2026-11-11）。

## Context

插件生命周期动作（安装、卸载、启用、重装）必然重启 worker。重启前 worker 会向
所有 WebSocket 客户端广播 `server:reconnect`，页面据此进入等待态并轮询
`/__health`。但这条链路只传递了「服务要关了」，没有传递「为什么关」：

- `requestRestart` 是 `() => void`，触发点知道原因却没有地方写。
- 广播载荷只有 `{ type: RECONNECT_EVENT }`。
- 连接状态机把「收到广播」与「连接意外关闭」合并成同一个 `reconnecting`。
- 外壳的状态条固定显示「正在重连…」，且直接操作 DOM，项目 body 拿不到连接。

结果是：用户自己点了「卸载」，界面却提示像服务掉线。应用侧也无法修正——状态条
不参与 React 树，连接实例也没有暴露给 body。这与「布局与界面归 body」的项目定位
相冲突。

## Decision

### 1. 原因由服务端产生，随协议送达

`server:reconnect` 的载荷增加可选 `reason`，类型为开放字符串，框架内置
`ReconnectReason`：

| 值 | 触发点 |
| --- | --- |
| `plugin-change` | 安装、卸载、启用、重装插件 |
| `restart` | `POST /api/restart` |
| `shutdown` | worker 收到 SIGTERM |
| `unexpected` | 客户端推断：没有收到广播的连接中断 |

原因只从框架内部的重启调用点产生（`requestRestart(reason)` / `restart(reason)`），
不接受 HTTP 请求参数注入。开放集合保证服务端以后新增原因时，旧客户端仍能解析并
回退为中性措辞。

### 2. 客户端状态分离相位与原因

`ConnectionState` 从字符串枚举改为 `{ phase, reason? }`：相位回答「现在能不能
用」，原因回答「为什么」。收到广播时采用服务端原因；连接意外关闭时标为
`unexpected`；恢复后清空原因，避免下一次意外断线沿用旧值。广播丢失时自然退化
为 `unexpected`，提示仍然成立。

### 3. 连接提示归 body

连接实例在 React 渲染前建立，建立后挂到 `ClientRuntime` 上；`useConnectionStatus()`
从运行时读取状态。壳不再直接挂 DOM 状态条：DefaultBody 渲染参考组件
`ConnectionStatusBar`，项目 body 可以用同一个 hook 完全替换措辞与位置。文案按
原因映射，未知原因为「正在重连…」。

## Alternatives

**客户端按「刚才点了什么」推断。** 动作响应后项目 UI 的忙碌状态立刻清空，而重启
在之后发生；CLI、多窗口或 `POST /api/restart` 触发的重启，项目 UI 根本不知道。
服务端是唯一知道原因的一方，让客户端猜会制造第二份真相。

**统一改成更轻的文案。** 把所有重连都说成「正在重新连接服务…」会掩盖真正的意外
掉线，用户无法判断是否需要采取行动。

**壳内置「插件变更」文案并保持 DOM 状态条。** 改动最小，但状态条仍然绕过 body，
项目既不能改位置也不能改措辞，与既有布局约定不一致。

## Consequences

正面：

- 用户主动操作引起的重启得到中性、可预期的提示；意外掉线保留「正在重连…」，
  失败仍是「连接已断开，请刷新页面」。
- 原因在协议里是一等数据，插件与项目都能消费，不需要再维护第三份推断逻辑。
- 连接提示与页面布局同属 body，项目可完全接管。

代价：

- `ConnectionState` 与 `onStateChange` 的签名变化；仓库内只有外壳一个调用方，
  但外部使用 `connect()` 的代码需要跟着调整。
- 重启调用链上的每个入口都必须声明原因；新增重启入口时容易漏写，缺省退化为
  `restart`，不会阻塞但文案会偏中性。
- SIGTERM 分不清外部是停止还是重启，只能用「正在等待服务恢复…」；真正停止时
  最终由 `failed` 给出明确提示。
